# 0.6.2 integrated ISO integrity note

**Scope:** evidence-only note. The final physically validated ISO was not changed or rebuilt during G1.

The standard clean-build path in `iso/build-atlasos.sh` creates a `SHA256SUMS` file in the binary tree after its GRUB EFI image is created and before making the ISO. Phase 6C is a separate integration/repack flow that starts with a known ISO, replaces/inserts the Atlas Boot Manager and backend EFI payload, then builds a candidate ISO.

The retained Phase 6C verification records the original/base hashes for `EFI/BOOT/BOOTX64.EFI` (`64284316a6105ccbb7d421fb6eb707cbe86eadfd43c0833d554fbfb5ca8bd06a`) and `boot/grub/efi.img` (`d393cbd74832d5f39d9952578a4bdbd44b9493451739f6969739a4481eae93b6`). The Phase 6C candidate frontend/backend hashes are recorded separately in its output checksums. The integration procedure preserved the embedded source manifest while replacing boot files; therefore those embedded entries are stale for at least the replaced EFI files. The changed files still booted on the user-reported successful physical path; an embedded checksum mismatch concerns offline file-integrity verification, not evidence of a boot failure. External final-ISO SHA-256 is a separate whole-artifact check.

The exact final ISO's embedded manifest was not re-extracted/recomputed in G1. Treat the stale-entry conclusion as a documented Phase 6C artifact finding, not a new independent full-ISO verification. G4 adds `iso/update-embedded-manifest.py` and wires it into the Phase 6C candidate script to refresh the root frontend, backend, and EFI image rows after integration. That future candidate fix does not rewrite the protected historical release ISO. G4 validated the manifest helper with temporary synthetic files; it did not run a new ISO integration or fully re-extract and validate every row of a new ISO.

Evidence source: `dist/validation/atlas-boot/phase6/6c/verification/ISO-SHA256SUMS` and Phase 6C build/verification scripts. Remediation belongs in G4/G6 and requires a new candidate build plus validation.

## G4.1 isolated candidate update (2026-10-05)

The G4.1 build-pipeline completion work produced a separate base ISO and integrated test candidate. Neither protected ISO above was intentionally targeted. Candidate: `dist/validation/g4.1/integrated/AtlasOS-0.6.2-g4.1-repro-test.iso`; size 3,475,963,904 bytes; SHA-256 `89523905f3e04814db2b6d0c34d141a45af8f0b50cef2dfc9dda72a5ffc1a492`, also stored in the adjacent `SHA256SUMS.txt`.

The final candidate's embedded manifest was extracted and validated in full (23/23 entries). ISO9660, BIOS and UEFI El Torito entries, hybrid metadata, EFI files/image, and Casper kernel/initrd/squashfs were present and readable. OVMF/QEMU reached the AtlasOS Live desktop after 180 seconds; a desktop capture is retained at `dist/validation/g4.1/qemu-ovmf/live-180s.png`. Between menu handoff and desktop capture, intermediate screenshots were black. None of the sampled captures shows a GRUB screen, but the snapshots cannot rule out a brief unobserved frame; Plymouth was not separately confirmed. This is only a virtual-machine result and does not establish behavior on physical hardware. In one 240-second SeaBIOS run the initial screenshot showed the ISOLINUX screen; after Enter, the capture remained black through the final frame and the Live desktop was not reached. Legacy BIOS boot therefore remains unvalidated despite the BIOS El Torito entry being present.

The frontend was built twice; both outputs are valid EFI binaries but their hashes differ, so bit-for-bit component repeatability was not demonstrated. Tool versions are recorded in `docs/build/toolchain.env`, but repository/package snapshots are not pinned and Level 2 environment control is not claimed. The complete ISO was built once; Level 3 is not claimed. G4.1's SeaBIOS path remained unvalidated; this is a known best-effort limitation and is not a release gate. UEFI is the primary supported boot path.
